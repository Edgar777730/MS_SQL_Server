# Лабораторная работа. Логины, пользователи, роли в MS SQL Server

Анализ создания логинов, пользователей и ролей в базе данных `college`.

## Слайд 13. Создание SQL-логина с отключённой политикой паролей

### Что требовалось
Показать, что при `CHECK_POLICY = OFF` SQL Server разрешает создание логина со слабым паролем, который обычно отклоняется политикой Windows.

### Что сделано
Выполнена команда:

    CREATE LOGIN dev1
    WITH PASSWORD = '12',
         DEFAULT_DATABASE = college,
         DEFAULT_LANGUAGE = [us_english],
         CHECK_EXPIRATION = OFF,
         CHECK_POLICY = OFF

Результат: `Выполнение команд успешно завершено.`

### Разбор параметров

| Параметр | Значение | Что означает |
|---|---|---|
| PASSWORD | '12' | Пароль — 2 символа (слабый) |
| DEFAULT_DATABASE | college | При входе пользователь попадает в college |
| DEFAULT_LANGUAGE | us_english | Язык сессии — английский |
| CHECK_EXPIRATION | OFF | Пароль не истекает |
| CHECK_POLICY | OFF | Политика паролей Windows НЕ проверяется |

### Анализ
Пароль '12' нарушает политику Windows: длина < 8 символов, нет заглавных букв, нет спецсимволов, нет комбинации букв и цифр.

При `CHECK_POLICY = ON` SQL Server отклонил бы создание с ошибкой:

    Msg 15116: Password validation failed. The password does not meet
    Windows policy requirements because it is too short.

Но `CHECK_POLICY = OFF` отключает проверку — слабый пароль разрешён.

### Сравнение режимов

| Параметр | CHECK_POLICY = OFF | CHECK_POLICY = ON |
|---|---|---|
| Пароль '12' | разрешён | отклонён (Msg 15116) |
| Длина >= 8 | не проверяется | проверяется |
| Сложность | не проверяется | проверяется |
| Срок действия | никогда | по политике |

### Вывод
`CHECK_POLICY = OFF` — опасная настройка. Позволяет создавать логины со слабыми паролями, что нарушает базовые требования безопасности. В продакшене использовать только `CHECK_POLICY = ON`.

## Слайд 14. Создание логина: GUI vs T-SQL

### Что требовалось
Показать два способа создания логина: через графический интерфейс SSMS и через T-SQL процедуру `sp_addlogin`.

### Что сделано

Способ 1 — через SSMS (GUI):
- Правый клик на Безопасность -> Пользователи -> Создать пользователя
- Тип: Пользователь SQL с именем для входа
- Имя: spfuser

Способ 2 — через T-SQL:

    EXEC sp_addlogin
        @loginame    = 'spfuser',
        @passwd      = 'ВашНадёжныйПароль123!',
        @defdb       = 'college',
        @deflanguage = 'us_english';

Результат: `Выполнение команд успешно завершено.`

### Разбор sp_addlogin

| Параметр | Значение | Что означает |
|---|---|---|
| @loginame | spfuser | Имя логина |
| @passwd | ВашНадёжныйПароль123! | Пароль |
| @defdb | college | База по умолчанию |
| @deflanguage | us_english | Язык по умолчанию |

### Анализ
`sp_addlogin` — устаревшая процедура (SQL Server 2005+). Microsoft рекомендует `CREATE LOGIN`:

    CREATE LOGIN spfuser
    WITH PASSWORD = 'ВашНадёжныйПароль123!',
         DEFAULT_DATABASE = college,
         DEFAULT_LANGUAGE = us_english;

### Отличия GUI vs T-SQL

| Способ | Плюсы | Минусы |
|---|---|---|
| GUI (SSMS) | Наглядно, автогенерация скрипта | Медленно для массовых операций |
| T-SQL | Быстро, воспроизводимо, версионируется | Требует знания синтаксиса |

### Вывод
Оба способа дают одинаковый результат. Для разовых операций удобен GUI, для повторяемых (CI/CD, миграции) — T-SQL. Устаревшие `sp_addlogin`/`sp_adduser` использовать не рекомендуется.

## Слайд 15. Создание пользователя БД и роли через GUI

### Что требовалось
Создать пользователя базы данных и роль через графический интерфейс SSMS.

### Что сделано

Часть 1 — Создание пользователя БД. Открыто окно «Пользователь базы данных — Создать» с разделами: Общие, Собственные схемы, Членство, Защищаемые объекты, Расширенные свойства.

Часть 2 — Выбор членства в ролях. В разделе «Членство» отображается список фиксированных ролей БД:

| Роль | Что даёт |
|---|---|
| db_accessadmin | Управление доступом к БД |
| db_backupoperator | Резервное копирование |
| db_datareader | Чтение всех таблиц |
| db_datawriter | Запись во все таблицы |
| db_ddladmin | Изменение структуры (DDL) |
| db_denydatareader | Запрет чтения |
| db_denydatawriter | Запрет записи |
| db_owner | Полные права в БД |
| db_securityadmin | Управление ролями и правами |

Часть 3 — Создание роли БД. Открыто окно «Роль базы данных — Создать»: имя роли, владелец, схемы, члены роли.

### Разбор фиксированных ролей БД

| Роль | Назначение |
|---|---|
| db_datareader | Только чтение (SELECT) |
| db_datawriter | Только запись (INSERT, UPDATE, DELETE) |
| db_owner | Полные права в базе |
| db_securityadmin | Управление разрешениями |
| db_ddladmin | Создание/изменение объектов |

Принцип минимальных привилегий: давать пользователю только те роли, которые нужны для его работы.

### Эквивалент в T-SQL

    USE college;
    GO

    CREATE USER spfuser FOR LOGIN spfuser;
    ALTER ROLE db_datareader ADD MEMBER spfuser;
    CREATE ROLE CustomReaderRole;
    GRANT SELECT ON dbo.STUDENT TO CustomReaderRole;

### Вывод
GUI SSMS — удобный инструмент для создания пользователей, ролей и разрешений. Он генерирует T-SQL под капотом. Для автоматизации и контроля версий лучше использовать T-SQL напрямую.

|---|---|

Ключевые принципы:
1. Логин — на уровне сервера, пользователь — на уровне базы.
2. CHECK_POLICY = ON — обязательное требование безопасности.
3. Фиксированные роли дают типовые наборы прав.
4. Пользовательские роли — точечные права на объекты.
5. GUI SSMS удобен для разовых операций, T-SQL — для автоматизации.
