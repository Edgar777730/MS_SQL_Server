# Лабораторная работа. Индексы в MS SQL Server

Анализ влияния индексов на производительность запросов в базе данных `college`.

---

## Задача 1. Создание кластеризованного индекса на heap-таблице

### Что требовалось
Дана таблица `dbo.Products` со 100 000 строк **без индексов (heap)**. Столбцы: `ProductID`, `Name`, `Price`, `CategoryID`. Требовалось создать кластеризованный индекс на `ProductID`, сравнить план выполнения и количество logical reads до и после.

### Что сделано
- Создана heap-таблица `dbo.Products` и заполнена 100 000 строками через `ROW_NUMBER()`.
- Выполнен запрос `SELECT * FROM dbo.Products WHERE ProductID = 50000` **до создания индекса**.
- Создан кластеризованный индекс `IX_Products_ProductID` на колонке `ProductID`.
- Выполнен тот же запрос **после создания индекса**.

### Результаты

| Этап | Операция в плане | Logical Reads |
|---|---|---|
| ДО индекса | Table Scan | ~395 |
| ПОСЛЕ индекса | Clustered Index Seek | ~3 |

### Анализ
**Heap** — таблица без индексов. SQL Server **не знает**, где лежит строка с `ProductID = 50000`, и вынужден **прочитать всю таблицу** (Table Scan).

**Кластеризованный индекс** физически упорядочивает строки по ключу `ProductID`. SQL Server спускается по B-дереву прямо к нужной строке — это **Clustered Index Seek**. Читаются только нужные страницы.

**Снижение logical reads: более чем в 100 раз.**

### Вывод
Кластеризованный индекс радикально ускоряет **точечный поиск** (`=`) по ключевой колонке. Для heap-таблиц любой точечный запрос = полное сканирование.

## Задача 2. Некластеризованный индекс для точечного поиска

### Что требовалось
Та же таблица `dbo.Products` с кластеризованным индексом на `ProductID`. Требовалось создать некластеризованный индекс на `Name`, выполнить `SELECT ProductID, Name, Price WHERE Name = N'Товар-777'` и определить, используется ли Key Lookup.

### Что сделано
- Создан некластеризованный индекс `IX_Products_Name` на колонке `Name`.
- Выполнен запрос с `SELECT ProductID, Name, Price`.
- Создан **покрывающий** индекс `IX_Products_Name_Inc` с `INCLUDE (ProductID, Price)`.
- Сравнены планы.

### Результаты

| Индекс | Операция в плане | Logical Reads | Key Lookup |
|---|---|---|---|
| `IX_Products_Name` | Index Seek + **Key Lookup** | ~7 | ✅ есть |
| `IX_Products_Name_Inc` | Index Seek (покрывающий) | ~3 | ❌ нет |

### Анализ
`IX_Products_Name` содержит только `Name` и ключ кластерного индекса (`ProductID`). Для колонки `Price`, которой **нет в индексе**, SQL Server делает **Key Lookup** — дополнительный заход в кластерный индекс за каждой строкой.

**Key Lookup** — дорогая операция: для каждой найденной строки выполняется отдельное чтение страницы кластерного индекса. Это снижает выигрыш от некластеризованного индекса.

**Решение** — `INCLUDE (Price)`: колонка `Price` хранится прямо в листьях некластеризованного индекса, и Key Lookup **не нужен**.

### Вывод
Некластеризованный индекс без `INCLUDE` решает задачу **частично** — поиск быстрый, но `SELECT` требует дополнительных чтений. Покрывающий индекс (`INCLUDE`) устраняет Key Lookup и делает запрос **полностью индексным**.

## Задача 3. Разница между Seek и Scan

### Что требовалось
Таблица `dbo.Orders` с 500 000 строк. Кластеризованный индекс на `OrderID`, некластеризованный на `CustomerID`. Выполнить три запроса и определить тип операции в плане.

### Что сделано
Создана таблица `dbo.Orders` (500 000 строк), кластерный индекс на `OrderID`, некластерный — на `CustomerID`. Выполнены три запроса:

1. `WHERE OrderID = 100`
2. `WHERE OrderID > 100 AND OrderID < 200`
3. `WHERE OrderID > 0`

### Результаты

| # | Запрос | Операция в плане | Logical Reads |
|---|---|---|---|
| 1 | `OrderID = 100` | Clustered Index Seek | ~3 |
| 2 | `OrderID BETWEEN 101 AND 199` | Clustered Index Seek (Range) | ~6 |
| 3 | `OrderID > 0` | Clustered Index Scan | ~3262 |

### Анализ
- **Запрос 1** — точечный поиск. SQL Server **точно знает** нужную строку → Seek.
- **Запрос 2** — диапазон. SQL Server находит **начало** диапазона по B-дереву и **читает подряд** до конца → Seek (Range).
- **Запрос 3** — условие подходит **почти для всех** строк. Дёшевле **прочитать всю таблицу**, чем идти по B-дереву → Scan.

Выбор оператора — **cost-based optimization**. Оптимизатор оценивает: сколько страниц придётся прочитать. Если «почти все» — выгоднее Scan.

### Вывод
`Seek` используется для **узкого** отбора (мало строк). `Scan` — когда **широкий** отбор (много строк). Это не «хорошо/плохо», а **стоимость операции**.

## Задача 4. Влияние selectivity на выбор индекса

### Что требовалось
Таблица `dbo.Users` с 200 000 строк. `Gender` содержит только 2 значения (M/F), `Email` уникален. Создать некластеризованные индексы на `Gender` и `Email`, сравнить планы двух запросов.

### Что сделано
- Создана таблица `dbo.Users` (200 000 строк).
- Созданы некластеризованные индексы `IX_Users_Gender` и `IX_Users_Email`.
- Выполнены два запроса:
  - `WHERE Gender = 'M'`
  - `WHERE Email = 'user777@test.com'`

### Результаты

| Запрос | Операция в плане | Logical Reads | Селективность |
|---|---|---|---|
| `WHERE Gender = 'M'` | **Clustered Index Scan** | ~1600 | 0.00% (2 значения) |
| `WHERE Email = 'user777@test.com'` | **Index Seek + Key Lookup** | ~7 | 100% (уникален) |

### Анализ
**Селективность** — доля строк, отбираемых условием.

- **`Gender = 'M'`** — условие отбирает ~50% строк (100 000). Индекс `IX_Users_Gender` **игнорируется**: дёшевле прочитать всю таблицу, чем делать 100 000 Key Lookup.
- **`Email = 'user777@test.com'`** — условие отбирает **1 строку**. `IX_Users_Email` находит её мгновенно.

**Правило:** индекс эффективен, когда условие отбирает **малую долю** строк (обычно **< 1–5%**).

### Вывод
Индекс — **не всегда** ускоряет запрос. Если селективность низкая (много строк под условие) — SQL Server **игнорирует** индекс. Планировщик оценивает стоимость и выбирает **оптимальный** путь. Для низкоселективных колонок (`Gender`, `Status`) индексы обычно **не нужны**.

## Общий вывод по лабораторной

| Задача | Что показала |
|---|---|
| 1 | Кластерный индекс → Seek вместо Scan для точечного поиска |
| 2 | Некластерный индекс + `INCLUDE` устраняет Key Lookup |
| 3 | Seek vs Scan зависит от **широты** отбора |
| 4 | Индекс используется только при **высокой селективности** |

**Главные принципы:**
1. **Heap** без индексов = полное сканирование.
2. **Кластерный** индекс на колонке **диапазона/точечного поиска** — обязателен.
3. **Покрывающий** индекс (`INCLUDE`) устраняет Key Lookup.
4. Индекс **не всегда** помогает — зависит от **селективности** и **стоимости**.
5. Планировщик SQL Server — **cost-based**: выбирает оператор по оценке стоимости.
