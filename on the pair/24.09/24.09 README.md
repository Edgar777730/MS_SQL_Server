# Транзакции и уровни изоляции в MS SQL Server

Анализ транзакций, SAVE TRANSACTION, @@TRANCOUNT и уровней изоляции
в базе данных college.

---

## Слайд 16. Простая транзакция с COMMIT

### Что требовалось
Показать работу транзакции: BEGIN TRANSACTION → INSERT → COMMIT.

### Что сделано

USE College;
GO

BEGIN TRANSACTION;

SELECT COUNT(*) FROM AUDITORIUM;          -- 10

INSERT INTO AUDITORIUM (AUDITORIUM, AUDITORIUM_TYPE, AUDITORIUM_CAPACITY, AUDITORIUM_NAME)
VALUES ('123-1', 'LECT', 60, '123-1');

SELECT COUNT(*) FROM AUDITORIUM;          -- 11

COMMIT;

SELECT COUNT(*) FROM AUDITORIUM;          -- 11

### Результат

| Шаг | COUNT(*) |
|---|---|
| До вставки | 10 |
| После вставки внутри транзакции | 11 |
| После COMMIT | 11 |

### Анализ
Транзакция начинается с BEGIN TRANSACTION. Внутри неё данные уже видны (COUNT = 11), но ещё не зафиксированы на диск. COMMIT фиксирует изменения — данные сохраняются.

### Вывод
Простая транзакция с COMMIT. Изменения видны внутри транзакции и сохраняются после фиксации.

## Слайд 17. Транзакция с ROLLBACK

### Что требовалось
Показать откат транзакции через ROLLBACK.

### Что сделано

USE College;
GO

BEGIN TRANSACTION;

SELECT COUNT(*) FROM AUDITORIUM;          -- 11

INSERT INTO AUDITORIUM (AUDITORIUM, AUDITORIUM_TYPE, AUDITORIUM_CAPACITY, AUDITORIUM_NAME)
VALUES ('128-1', 'LECT', 60, '128-1');

SELECT COUNT(*) FROM AUDITORIUM;          -- 12

ROLLBACK;

SELECT COUNT(*) FROM AUDITORIUM;          -- 11

### Результат

| Шаг | COUNT(*) |
|---|---|
| До вставки | 11 |
| После вставки внутри транзакции | 12 |
| После ROLLBACK | 11 |

### Анализ
ROLLBACK отменяет все изменения с момента BEGIN TRANSACTION. Вставка «128-1» исчезла — COUNT вернулся к 11.

### Вывод
ROLLBACK полностью откатывает транзакцию. Это основа атомарности.

## Слайд 18. SAVE TRANSACTION (точки сохранения)

### Что требовалось
Показать частичный откат через SAVE TRANSACTION.

### Что сделано

USE College;
GO

DELETE FROM AUDITORIUM WHERE AUDITORIUM IN ('127-1', '128-1', '129-1', '130-1');
GO

BEGIN TRANSACTION;

INSERT INTO AUDITORIUM VALUES ('127-1', 'LECT', 60, '127-1');
SAVE TRANSACTION A;

INSERT INTO AUDITORIUM VALUES ('128-1', 'PRAC', 60, '128-1');
SAVE TRANSACTION B;

INSERT INTO AUDITORIUM VALUES ('129-1', 'LECT', 60, '129-1');
ROLLBACK TRANSACTION B;

INSERT INTO AUDITORIUM VALUES ('130-1', 'PRAC', 60, '130-1');
ROLLBACK TRANSACTION A;

COMMIT TRANSACTION;

SELECT * FROM AUDITORIUM
WHERE AUDITORIUM IN ('127-1', '128-1', '129-1', '130-1');

### Результат

| AUDITORIUM | AUDITORIUM_TYPE | AUDITORIUM_CAPACITY | AUDITORIUM_NAME |
|---|---|---|---|
| 127-1 | LECT | 60 | 127-1 |

**Только `127-1` сохранилась.**

### Анализ
- SAVE TRANSACTION A — метка после вставки 127-1.
- SAVE TRANSACTION B — метка после вставки 128-1.
- ROLLBACK B — откат до метки B (удаляет 129-1).
- ROLLBACK A — откат до метки A (удаляет 128-1 и 130-1).
- COMMIT — фиксирует только то, что было **до** метки A.

### Вывод
SAVE TRANSACTION позволяет **частично** откатывать транзакцию. До COMMIT сохраняется только то, что было вставлено до первой метки.

## Слайд 23. @@TRANCOUNT и вложенные транзакции

### Что требовалось
Показать работу @@TRANCOUNT при вложенных BEGIN/COMMIT.

### Что сделано

USE College;
GO

BEGIN TRANSACTION A;

INSERT INTO AUDITORIUM VALUES ('128-1', 'PRAC', 60, '128-1');
SELECT COUNT(*) AS '2', @@TRANCOUNT AS 'TRANCOUNT' FROM AUDITORIUM;   -- 12, 1

BEGIN TRANSACTION B;
DELETE FROM AUDITORIUM WHERE AUDITORIUM = '128-1';
SELECT COUNT(*) AS '3', @@TRANCOUNT AS 'TRANCOUNT' FROM AUDITORIUM;   -- 11, 2

COMMIT TRANSACTION B;
SELECT COUNT(*) AS '4', @@TRANCOUNT AS 'TRANCOUNT' FROM AUDITORIUM;   -- 11, 1

INSERT INTO AUDITORIUM VALUES ('128-1', 'PRAC', 60, '128-1');
SELECT COUNT(*) AS '5', @@TRANCOUNT AS 'TRANCOUNT' FROM AUDITORIUM;   -- 12, 1

COMMIT TRANSACTION A;
SELECT COUNT(*) AS '6', @@TRANCOUNT AS 'TRANCOUNT' FROM AUDITORIUM;   -- 12, 0

### Результат

| # | COUNT(*) | TRANCOUNT |
|---|---|---|
| 1 | 11 | 0 |
| 2 | 12 | 1 |
| 3 | 11 | 2 |
| 4 | 11 | 1 |
| 5 | 12 | 1 |
| 6 | 12 | 0 |

### Анализ
@@TRANCOUNT считает **число активных транзакций**. BEGIN увеличивает счётчик, COMMIT — уменьшает. Вложенный COMMIT B не фиксирует данные на диск — только уменьшает счётчик. Реальная фиксация — только при COMMIT A.

### Вывод
@@TRANCOUNT — счётчик уровня вложенности. Реальная фиксация происходит только при внешнем COMMIT (когда счётчик станет 0).

## Слайд 35 (Окно 1). Анализ блокировок

### Что требовалось
Посмотреть активные блокировки через sys.dm_tran_locks.

### Что сделано

USE College;
GO

SELECT
    resource_type,
    DB_NAME(resource_database_id) AS database_name,
    request_session_id,
    request_mode,
    request_status
FROM sys.dm_tran_locks;

### Результат

| resource_type | database_name | request_session_id | request_mode | request_status |
|---|---|---|---|---|
| DATABASE | college | 71 | S | GRANT |
| DATABASE | college | 77 | S | GRANT |

### Анализ
DATABASE + S (Shared) — разделяемая блокировка на уровне базы. Она есть у каждого соединения. Показывает, что две сессии подключены к college.

### Вывод
sys.dm_tran_locks даёт обзор активных блокировок. На уровне DATABASE — S-блокировки от активных сессий.

## Слайд 35 (Окна 1 и 2). Взаимоблокировка (DEADLOCK)

### Что требовалось
Воспроизвести deadlock между двумя сессиями.

### Что сделано

**Окно 1:**

BEGIN TRANSACTION;
UPDATE AUDITORIUM SET AUDITORIUM_TYPE = 'PRAC' WHERE AUDITORIUM_NAME = '128-1';
WAITFOR DELAY '00:00:10';
UPDATE AUDITORIUM SET AUDITORIUM_CAPACITY = 70 WHERE AUDITORIUM_NAME = '127-1';
COMMIT;

**Окно 2 (параллельно):**

BEGIN TRANSACTION;
UPDATE AUDITORIUM SET AUDITORIUM_TYPE = 'LECT' WHERE AUDITORIUM_NAME = '127-1';
WAITFOR DELAY '00:00:10';
UPDATE AUDITORIUM SET AUDITORIUM_CAPACITY = 66 WHERE AUDITORIUM_NAME = '128-1';
COMMIT;

### Результат
Окно 1 захватывает блокировку на «128-1», Окно 2 — на «127-1». Затем оба пытаются обновить строку другого → **циклическое ожидание** → SQL Server выбирает **жертву** и откатывает одну из транзакций:

Msg 1205: Transaction was deadlocked on lock resources with another process and has been chosen as the deadlock victim.

### Анализ
Deadlock возникает при **взаимном** захвате ресурсов. SQL Server обнаруживает цикл и разрывает его через откат одной транзакции.

### Вывод
Deadlock — неизбежен при конкурентном доступе. Решение — единый порядок доступа к ресурсам или меньшие транзакции.

## Слайд 45 (Окна 1–4). READ UNCOMMITTED — грязное чтение

### Что требовалось
Показать грязное чтение при READ UNCOMMITTED.

### Что сделано

**Окно 1:**
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN TRAN;
SELECT COUNT(*) FROM AUDITORIUM;   -- 13

**Окно 2:**
BEGIN TRAN;
DELETE FROM AUDITORIUM WHERE AUDITORIUM = '128-1';

**Окно 3:**
SELECT COUNT(*) FROM AUDITORIUM;   -- 12 (видит незакоммиченное удаление)

**Окно 4:**
ROLLBACK TRAN;

**Окно 5:**
SELECT COUNT(*) FROM AUDITORIUM;
COMMIT TRAN;

### Результат

| Шаг | COUNT(*) | Событие |
|---|---|---|
| 1 | 13 | Окно 1 — старт транзакции |
| 2 | — | Окно 2 — DELETE без COMMIT |
| 3 | 12 | Окно 3 — видит незакоммиченное удаление |
| 4 | — | Окно 4 — ROLLBACK |
| 5 | 13 | Окно 5 — данные вернулись |

### Анализ
READ UNCOMMITTED позволяет читать **незакоммиченные** данные другой транзакции. Окно 3 «увидело» удаление, которое потом откатилось. Это **грязное чтение (dirty read)**.

### Вывод
READ UNCOMMITTED даёт максимальный параллелизм, но риск чтения **несуществующих** данных.

## Слайд 48 (Окна 6–9). READ COMMITTED — блокировка

### Что требовалось
Показать, что READ COMMITTED **не допускает** грязного чтения.

### Что сделано

**Окно 6:**
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRAN;
SELECT COUNT(*) FROM AUDITORIUM;   -- 13

**Окно 7:**
BEGIN TRAN;
DELETE FROM AUDITORIUM WHERE AUDITORIUM = '128-1';

**Окно 8:**
SELECT COUNT(*) FROM AUDITORIUM;   -- зависает — ждёт снятия блокировки

**Окно 9:**
ROLLBACK TRAN;

### Результат

| Шаг | COUNT(*) | Событие |
|---|---|---|
| 1 | 13 | Окно 6 — старт транзакции |
| 2 | — | Окно 7 — DELETE без COMMIT |
| 3 | завис | Окно 8 — ждёт (READ COMMITTED) |
| 4 | — | Окно 9 — ROLLBACK |
| 5 | 13 | Окно 8 разблокировано |

### Анализ
READ COMMITTED **не даёт** читать незакоммиченные данные. Окно 8 **ждёт** снятия X-блокировки от Окна 7.

### Вывод
READ COMMITTED защищает от грязного чтения ценой **блокировки** читателя.

## Общий вывод

| Слайд | Что показал |
|---|---|
| 16 | COMMIT — фиксация изменений |
| 17 | ROLLBACK — полный откат |
| 18 | SAVE TRANSACTION — частичный откат |
| 23 | @@TRANCOUNT — счётчик вложенности |
| 35 | sys.dm_tran_locks — анализ блокировок |
| 35 | DEADLOCK — взаимоблокировка |
| 45 | READ UNCOMMITTED — грязное чтение |
| 48 | READ COMMITTED — блокировка |

**Ключевые принципы:**
1. COMMIT фиксирует, ROLLBACK откатывает.
2. SAVE TRANSACTION — точки сохранения внутри транзакции.
3. @@TRANCOUNT — уровень вложенности (реальная фиксация только при 0).
4. Deadlock — циклическое ожидание блокировок.
5. READ UNCOMMITTED — грязное чтение, READ COMMITTED — блокировка.
