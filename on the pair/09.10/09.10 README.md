# Лабораторная работа. Логины, пользователи, роли в MS SQL Server

Анализ работы с логинами, пользователями, ролями и разрешениями в базе данных `college`.

---

## Задание 1. Создание SQL-логина с политикой паролей

Создан логин `TestUser01` с паролем `P@ssw0rd123!`, `CHECK_POLICY = ON`, `CHECK_EXPIRATION = OFF`, `DEFAULT_DATABASE = master`.

**Проверка через `sys.sql_logins`:**

| Логин | Тип | Проверка политики | Проверка срока | База |
|---|---|---|---|---|
| TestUser01 | SQL_LOGIN | **1** | 0 | master |

**Анализ:** `is_policy_checked = 1` — политика включена. Пароль соответствует требованиям: длина 12, есть заглавные/строчные/цифры/спецсимволы.

**Вывод:** логин создан с соблюдением политики сложности. Вход под `TestUser01` успешен, доступ к `master` подтверждён.

## Задание 2. Создание логина Windows и сопоставление с пользователем БД

Создан логин `DESKTOP-7JGCBJA\Edgar` (`FROM WINDOWS`). В базе `college` создан пользователь `Edgar`, связанный с этим логином. Пользователь добавлен в роль `db_datareader`.

**Проверка:**

| Логин | Тип | База |
|---|---|---|
| DESKTOP-7JGCBJA\Edgar | WINDOWS_LOGIN | college |

| Пользователь | Тип | Схема |
|---|---|---|
| Edgar | SQL_USER | dbo |

| Роль | Пользователь |
|---|---|
| db_datareader | Edgar |

**Анализ:** логин — на уровне сервера, пользователь — на уровне базы. Один логин может иметь разных пользователей в разных базах.

**Вывод:** Windows-логин успешно сопоставлен с пользователем БД. Разделение «логин / пользователь» позволяет управлять правами в разных базах.

## Задание 3. Создание пользователя без логина

Создан пользователь `AppServiceUser` с `WITHOUT LOGIN` в базе `college`. Добавлен в роль `db_datareader`.

**Проверка:**

| Пользователь | Тип | SID | Схема |
|---|---|---|---|
| AppServiceUser | SQL_USER | 0x… | dbo |

**Логин на сервере** — пусто (логина нет).

**Демонстрация `EXECUTE AS USER`:**

| До | После | После REVERT |
|---|---|---|
| dbo | AppServiceUser | dbo |

**Анализ:** `WITHOUT LOGIN` — пользователь существует только в базе, не может подключаться к серверу. Используется для `EXECUTE AS`, подписи модулей, владения схемой.

**Вывод:** такой пользователь — удобный контейнер прав. Ограничение — невозможность прямого подключения.

## Задание 4. Создание логина с истёкшим сроком действия пароля

Создан логин `TempUser` с `CHECK_EXPIRATION = ON`, `CHECK_POLICY = ON`. Пароль помечен как `MUST_CHANGE`.

**Проверка через `LOGINPROPERTY`:**

| Логин | Политика | Срок | Требует смены | Истёк | Заблокирован |
|---|---|---|---|---|---|
| TempUser | 1 | 1 | **1** | 0 | 0 |

**Анализ:** `IsMustChange = 1` — имитация истёкшего пароля. При входе SQL Server вернёт `Msg 18488: The password must be changed before logging in the first time`.

**Вывод:** `MUST_CHANGE` даёт тот же эффект, что истёкший пароль — вход невозможен без смены. Реальное истечение (42 дня) воспроизвести сложно.

## Задание 6. Добавление логина в фиксированную серверную роль

Логин `TestUser01` добавлен в роль `securityadmin`.

**Проверка членства:**

| Роль | Логин |
|---|---|
| securityadmin | TestUser01 |

**Права роли `securityadmin`:**
- `CREATE LOGIN` / `ALTER LOGIN` / `DROP LOGIN`
- `GRANT` / `DENY` / `REVOKE` на уровне сервера
- управление разрешениями на уровне БД
- сброс паролей SQL-логинов

**Анализ:** `securityadmin` — **мощная** роль. Фактически может выдать себе любые права через `GRANT`. Microsoft рекомендует относиться к ней как к `sysadmin`.

**Вывод:** роль даёт полный контроль над безопасностью сервера. Использовать с осторожностью.

## Задание 7. Создание пользовательской серверной роли

Создана роль `CustomServerRole`, ей выдано право `ALTER ANY LOGIN`. Логин `TestUser01` добавлен в роль.

**Проверка:**

| Роль | Член роли |
|---|---|
| CustomServerRole | TestUser01 |

| Роль | Состояние | Право |
|---|---|---|
| CustomServerRole | GRANT | ALTER ANY LOGIN |

**Проверка через `fn_my_permissions`:** у `TestUser01` есть `ALTER ANY LOGIN`.

**Анализ:** пользовательская роль с точечным правом. `TestUser01` теперь **может создавать логины**.

**Вывод:** пользовательские роли позволяют выдавать **конкретные** права без избыточных полномочий фиксированных ролей.

## Задание 9. Удаление логина из роли и удаление пользовательской роли

`TestUser01` удалён из `securityadmin` и `CustomServerRole`. Роль `CustomServerRole` удалена.

**Проверка до:**

| Роль | Логин |
|---|---|
| securityadmin | TestUser01 |
| CustomServerRole | TestUser01 |

**После:** пользовательских ролей нет.

**Условия для удаления роли:**
1. Роль **пуста** (нет членов).
2. Роль **не владеет** объектами.
3. Роль **не фиксированная**.
4. Есть право `ALTER ANY SERVER ROLE`.

**Вывод:** удаление роли — двухшаговая операция: очистить от членов → `DROP SERVER ROLE`. Фиксированные роли удалить нельзя.

## Задание 11. Создание пользовательской роли с точечными правами

Создана роль `SalesRole` с правами `SELECT`, `INSERT`, `UPDATE` на `dbo.STUDENT`. `JohnDoe` добавлен в роль.

**Права роли:**

| Роль | Право | Состояние | Объект |
|---|---|---|---|
| SalesRole | INSERT | GRANT | STUDENT |
| SalesRole | SELECT | GRANT | STUDENT |
| SalesRole | UPDATE | GRANT | STUDENT |

**Проверки:**
- ✅ `SELECT` — работает
- ✅ `INSERT` — работает
- ✅ `UPDATE` — работает
- ❌ `DELETE` — **отклонён** (права нет)

**Анализ:** точечные права дают **ровно то, что нужно**. `DELETE` не выдан — удаление невозможно.

**Вывод:** принцип минимальных привилегий. Пользовательская роль — гибкий инструмент для точной настройки прав.

## Задание 12. Запрет (DENY) на уровне объекта

Создан пользователь `RestrictedUser`. Ему выдан `GRANT SELECT ON SCHEMA::Sales`, но `DENY SELECT ON Sales.CreditCard`.

**Права:**

| Пользователь | Право | Состояние | Уровень | Объект |
|---|---|---|---|---|
| RestrictedUser | SELECT | GRANT | SCHEMA | Sales |
| RestrictedUser | SELECT | **DENY** | OBJECT | CreditCard |

**Проверки:**
- ✅ `SELECT` из `Sales.Orders` — работает (право через схему)
- ❌ `SELECT` из `Sales.CreditCard` — **отклонён** (`Msg 229`)

**Анализ:** **`DENY` приоритетнее `GRANT`**. Даже при праве на всю схему явный `DENY` на таблицу перекрывает его.

**Вывод:** точечный `DENY` позволяет запретить доступ к **чувствительным** данным без изменения общих прав.

## Задание 13. Права на выполнение хранимых процедур

Создан пользователь `AppServiceUser`. Созданы две процедуры. Выдан `EXECUTE` только на `uspGetEmployeeManagers`.

**Права:**

| Пользователь | Право | Состояние | Объект |
|---|---|---|---|
| AppServiceUser | CONNECT | GRANT | NULL |
| AppServiceUser | EXECUTE | GRANT | uspGetEmployeeManagers |

**Проверки:**
- ✅ `EXEC uspGetEmployeeManagers` — **работает**
- ❌ `EXEC uspGetAllStudents` — **отклонён** (`Msg 229`)

**Анализ:** право `EXECUTE` выдаётся **точечно** — на конкретную процедуру. `AppServiceUser` может вызывать только разрешённый код.

**Вывод:** точечные права на процедуры — стандартный приём для сервисных учёток. Пользователь не имеет доступа к таблицам напрямую, но может выполнять разрешённые операции через процедуру.
