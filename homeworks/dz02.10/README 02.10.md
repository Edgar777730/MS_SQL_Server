# Лабораторная работа. Транзакции (BEGIN/COMMIT/ROLLBACK, TRY/CATCH, SAVE, уровни изоляции)

Анализ задач по транзакциям, обработке ошибок, вложенным транзакциям,
уровням изоляции в базе данных college.

## Задание 1. Основы транзакций (BEGIN/COMMIT/ROLLBACK)

### Что требовалось
Создать таблицу Accounts с полями AccountId, OwnerName, Balance. Наполнить тремя счетами. Написать успешную транзакцию (перевод 1000 руб.) и транзакцию с ошибкой → ROLLBACK. Объяснить, почему откат сработал.

### Что сделано
Создана таблица Accounts с CHECK (Balance >= 0). Три счёта: 5000, 3000, 7000.

Успешная транзакция — списание 1000 со счёта 1, зачисление на счёт 2, COMMIT.

Транзакция с ошибкой — списание 1000 со счёта 1, списание 9000 со счёта 3 (при балансе 7000), COMMIT. CHECK нарушается, CATCH выполняет ROLLBACK.

### Результат
Успешная: балансы 4000, 4000, 7000.
С ошибкой: ошибка CHECK, ROLLBACK — балансы вернулись к исходным.

### Анализ
- Транзакция — единое целое: пока нет COMMIT, изменения не зафиксированы.
- CHECK (Balance >= 0) сработал на втором UPDATE.
- Ошибка поймана в CATCH → ROLLBACK.
- ROLLBACK откатил ВСЕ изменения с момента BEGIN TRANSACTION, включая первый успешный UPDATE.

### Вывод
Транзакции обеспечивают атомарность (ACID). При ошибке в любой операции вся транзакция откатывается — база остаётся согласованной.

## Задание 2. Обработка ошибок с TRY...CATCH и XACT_ABORT

### Что требовалось
Реализовать перевод денег внутри TRY...CATCH. В CATCH — ROLLBACK, вывод ERROR_NUMBER() и ERROR_MESSAGE(). Протестировать поведение с XACT_ABORT ON и OFF. Описать разницу.

### Что сделано

**Тест 1 — успешный перевод:**
BEGIN TRY, BEGIN TRAN, два UPDATE, COMMIT. Результат — балансы 4000 и 4000.

**Тест 2 — XACT_ABORT OFF:**
SET XACT_ABORT OFF. Перевод с ошибкой CHECK. В CATCH: ROLLBACK, вывод ERROR_NUMBER() и ERROR_MESSAGE().

**Тест 3 — XACT_ABORT ON:**
SET XACT_ABORT ON. Тот же перевод с ошибкой. При ошибке SQL Server автоматически откатил транзакцию ДО CATCH.

### Результат

| Тест | XACT_ABORT | Поведение |
|---|---|---|
| 1 | — | COMMIT, балансы изменились |
| 2 | OFF | ROLLBACK в CATCH, ручной откат |
| 3 | ON | SQL Server сам откатил, CATCH не делает ROLLBACK |

### Анализ

XACT_ABORT OFF — при ошибке откатывается только проблемный оператор, транзакция остаётся активной. Нужен явный ROLLBACK.

XACT_ABORT ON — при любой ошибке SQL Server автоматически откатывает всю транзакцию. @@TRANCOUNT уже 0 в CATCH.

### Вывод
Для критичных операций (финансовых) рекомендуется XACT_ABORT ON — гарантия атомарности. Проверка IF @@TRANCOUNT > 0 ROLLBACK работает в обоих режимах.

## Задание 3. Вложенные транзакции и SAVE TRANSACTION

### Что требовалось
Смоделировать три операции в одной транзакции: списание со счёта A, зачисление на счёт B, запись в TransferLog. Использовать SAVE TRANSACTION SavePoint1 после шага 1. При ошибке на шаге 3 — откат только к SavePoint1. Вопрос: почему ROLLBACK SavePoint1 не уменьшает @@TRANCOUNT?

### Что сделано
Созданы таблицы Accounts и TransferLog (с CHECK Amount > 0). В транзакции: списание со счёта A, SAVE TRANSACTION SavePoint1, зачисление на счёт B, запись в лог с отрицательной суммой. CHECK нарушается → CATCH → ROLLBACK SavePoint1.

### Результат
Шаги 1 и 2 сохранены, шаг 3 откатился. @@TRANCOUNT остался равен 1.

### Анализ
SAVE TRANSACTION не создаёт новую транзакцию — это только метка внутри текущей. ROLLBACK TRANSACTION SavePoint1 не откатывает всю транзакцию, только операции после метки. Поэтому @@TRANCOUNT не уменьшается.

### Ответ на вопрос
ROLLBACK TRANSACTION SavePoint1 не уменьшает @@TRANCOUNT, потому что SAVE TRANSACTION не создаёт новую транзакцию. Это лишь точка сохранения внутри текущей. Транзакция остаётся активной — счётчик не меняется.

### Вывод
SAVE TRANSACTION удобен для частичного отката внутри большой транзакции.

## Задание 4. Уровни изоляции и аномалии чтения

### Что требовалось
Создать таблицу Products. В первой сессии обновить остаток без COMMIT. Во второй сессии читать при разных уровнях изоляции. Заполнить таблицу: уровень → поведение. Сделать вывод для складского учёта.

### Что сделано

Включён SNAPSHOT для базы college.

Создана таблица Products (ProductID, Name, Stock, CHECK Stock >= 0). Три товара: Ноутбук 10, Монитор 25, Клавиатура 50.

Проведены тесты:

- READ UNCOMMITTED — сессия 2 видит Stock = 7 (незакоммиченное). Грязное чтение.
- READ COMMITTED — сессия 2 ждёт COMMIT/ROLLBACK.
- REPEATABLE READ — S-блокировка до конца транзакции.
- SNAPSHOT — сессия 2 видит Stock = 10 (снимок на момент старта).

### Результат

| Уровень | Что видит | Блокировка | Аномалия |
|---|---|---|---|
| READ UNCOMMITTED | 7 (незакоммичено) | Нет | Грязное чтение |
| READ COMMITTED | Ждёт | S-блокировка | Защита от грязного |
| REPEATABLE READ | Ждёт | S до конца | Защита от non-repeatable |
| SNAPSHOT | 10 (снимок) | Нет | Согласованный снимок |

### Анализ
READ UNCOMMITTED опасен: можно увидеть откаченные данные. READ COMMITTED защищает, но блокирует чтение. SNAPSHOT — компромисс: согласованный снимок без блокировок.

### Вывод для складского учёта
Для оперативного учёта — READ COMMITTED. Для длинных отчётов (инвентаризация) — SNAPSHOT. READ UNCOMMITTED использовать нельзя — риск ошибок в остатках.

**Ключевые принципы ACID:**
1. Atomicity — всё или ничего.
2. Consistency — ограничения (CHECK, UNIQUE).
3. Isolation — уровни изоляции.
4. Durability — COMMIT фиксирует на диск.

**XACT_ABORT:**
- OFF — ошибка откатывает только оператор, транзакция остаётся.
- ON — ошибка автоматически откатывает всю транзакцию.

**SAVE TRANSACTION:**
- Точка сохранения внутри транзакции.
- ROLLBACK к метке не уменьшает @@TRANCOUNT.

**Уровни изоляции:**
- READ UNCOMMITTED — грязное чтение.
- READ COMMITTED — блокировка читателя.
- REPEATABLE READ — S-блокировка до конца.
- SERIALIZABLE — полная изоляция.
- SNAPSHOT — снимок без блокировок.
